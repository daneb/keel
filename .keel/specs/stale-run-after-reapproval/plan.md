# Design — stale-run-after-reapproval

## Approach

The seam is `pipeline::passing_run` in `src/pipeline.rs`, the one function
that decides whether a spec's Run stage is satisfied. Today it returns the
newest run whose G2 passed and never looks at approvals. It will also drop any
run whose `started_at` (`RunMeta`, `src/run.rs`) precedes the current spec
approval or the current plan approval timestamp. This mirrors the existing
`g1_stale` rule in `position`, which compares a G1 result's `generated_at`
with the spec approval's `at`, applied one stage later and to both approvals.

`position` already reads both approvals before calling `passing_run`, so they
are passed in rather than re-read. When the newest passing run is dropped for
being older than an approval, `position` keeps its id in a new
`Position::stale_run: Option<String>`, beside `g1_stale`. `derive_stage` is
unchanged: with no passing run it already returns `Stage::Run`, which gives
AC-1 and AC-2, and a run newer than both approvals still yields
`MergeApproval`, which is AC-3.

`keel next` reads the same `Position`, so it cannot disagree with the stage.
`src/cmd/next.rs` adds `"stale_run": "<run id>"` to that spec's entry in
`--json`, leaving the `keel.next/1` schema string alone, and prints a text line
naming the stale run and `keel run <slug>`, in the way the `g1_stale` branch
already explains itself. No other consumer is changed.

Ordering: T-1 changes `src/pipeline.rs` first, with the plan-approval test
that proves it. T-2 and T-3 add the spec-approval and still-counts cases in
`tests/pipeline.rs`. T-4 and T-5 surface the result in `keel next` and are
tested last. Every task edits `tests/pipeline.rs` or `src/pipeline.rs`, so the
tasks are chained.

Risk: the comparison is between RFC 3339 timestamps from different sources
(`started_at` uses the local offset), so it must parse them rather than
compare strings. Task budgets total 215 of the 250 lines, leaving 35 for that.
