# Design — spec-abandonment

## Approach

The seam is `pipeline::derive_stage` (src/pipeline.rs). Today it reads only
gates and approvals; it never consults `SpecFront.status`. The whole change
hangs off adding one terminal variant and one early return.

1. **`Stage::Abandoned` (src/pipeline.rs).** Add the variant *after* `Complete`
   so the derived `Ord` keeps it terminal (AC-8). Give it `key() = "abandoned"`
   and a distinct `label()` (AC-7). `pipeline::position` takes the spec's
   `status` as an input and, when it is `abandoned`, returns `Abandoned` before
   any gate/approval logic (AC-1). Because the status is read, not persisted in
   the `Position`, clearing it back to `draft` restores the derived stage with
   no evidence loss (AC-6) — the gate and approval files are never touched by
   abandonment.

2. **Recording (src/approval.rs).** Extend the sign-off log rather than invent a
   second one, so abandonment is auditable beside approvals. Add an `abandon`
   stage to `artefact_names` (hashing `spec.md`, like the spec stage) and let
   `record` carry it; the reason rides in the existing `note` field and `by`
   is the existing `current_user`. No new schema.

3. **Command (src/cmd/spec.rs, src/main.rs).** Add `keel spec abandon <slug>
   --reason <why> [--force]`. It refuses an empty/whitespace reason (AC-4),
   refuses a `Complete` spec unless `--force` (AC-5, mirroring the completed-spec
   lock already in `cmd/approve.rs`), writes `status: abandoned` into the spec
   front matter via `store::frontmatter`, and calls `approval::record`.

4. **Enumeration (src/cmd/next.rs).** `run_json` already sets
   `complete: stage == Stage::Complete`. Widen that to treat `Abandoned` as
   complete too (AC-2), so any consumer filtering on `!complete` — including
   moor's `guide::pick_active` — drops it from the open set. The human-readable
   `keel next` path already filters `!= Stage::Complete`; extend it the same way.

5. **Tests (tests/pipeline.rs).** One test per AC, names matching the oracles.

The status write is the only new mutation of `spec.md`; everything else is
additive. No existing stage, gate, or approval semantics change.

## Rollback

`git revert` of the implementing commits. The change is additive (a new
terminal stage and a new command); reverting restores the prior `Stage` enum
and leaves any `status: abandoned` front-matter values inert — they are read
only by code the revert removes, so a reverted tree treats those specs as
open again exactly as it did before.
