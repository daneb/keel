# Design — copilot-credential-preflight

## Approach

The seam is the point in `.keel/drivers/copilot` *between* reading the task and
invoking `copilot -p` — specifically before `copilot` runs and, in a wave run,
before any worktree is created. Today that gap holds nothing; the driver learns
a credential is bad only from the agent's failure output.

Add a `keel_copilot_preflight` helper to `.keel/drivers/_common.sh` (the shared
place these adapters already source) and call it in the copilot driver before
the `copilot -p` invocation. The helper decides on the credential alone:

- Resolve the credential in the CLI's own precedence: `COPILOT_GITHUB_TOKEN`,
  then `GH_TOKEN`, then `GITHUB_TOKEN`.
- A token beginning `ghp_` (classic PAT) is rejected: `keel_emit blocked` and
  return non-zero so the driver exits before `copilot -p` (AC-1).
- No resolved credential at all: `keel_emit blocked` and return non-zero (AC-3).
- Any block message names the fix verbatim — `copilot /login` on the host
  (AC-2).
- A token beginning `gho_` (device-flow) passes; the helper returns 0 and the
  driver proceeds to `copilot -p`, whose own result decides the run (AC-4).

Enterprise host (AC-5): the driver continues to let `COPILOT_GH_HOST`/`GH_HOST`
reach the CLI through the inherited environment; the preflight does not strip or
override them. Ordering (AC-6): because the helper is called at the top of the
driver — the driver that keel runs inside each worktree only after this returns
0 — a failed preflight exits before `.keel/worktrees/` gains an entry.

The existing post-invocation auth `case` stays as a backstop for failures the
preflight cannot see (an expired but well-formed `gho_` token, a server-side
rejection), so no behaviour is removed, only moved earlier.
