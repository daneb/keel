# Design — ci-runtime

## Approach

The host's work goes in a new `src/runtime/host.rs`, next to the posture
preflight keel already has in `src/runtime/`. The GitHub specifics live in
`runtime/action.yml`, and nothing in Rust knows it's in CI except the
`GITHUB_*` identity.

**`keel runtime fold` (AC-1).** `host::fold(sink, chain, writer)` reads sink
lines from the offset in `<chain>.sink-offset`, resetting the offset when the
sink got shorter. It appends each `{kind, data}` through `chain::append(chain,
kind, writer, data)` with `source: "sandbox"` added, and appends anything else
as `sink_malformed`. The same rules as Moor's fold, in keel's code.

**`keel runtime attest` (AC-2 to AC-4).** `host::derive(inspect)` is pure over
one `docker inspect` object. It uses Moor's property rules (read-only root,
privileged, bind mounts named as evidence, non-root user, all capabilities
dropped, no-new-privileges), plus:
- `network.internal_only`: proven for `--network none` or all-internal
  networks, violated for `bridge`, with the network names as evidence.
- `kernel.isolated`: proven only when `HostConfig.Runtime` is `runsc`,
  unproven otherwise (AC-3).

`attest` writes `keel.posture/1` with `runtime: "github-actions"`, the image
digest, the properties, and `runtime_identity { claimed_by: "runner",
repository, workflow, run_id, sha }` from the `GITHUB_*` variables that are set
(AC-4). It then appends `attest { sha256, properties }` to the chain.
`schemas/posture.json` gains `runtime_identity` as an optional object.

**`runtime/action.yml` (AC-5 to AC-7).** A composite action with inputs `spec`
(required), `image` (required: the repository's toolchain image), `network`
(`bridge`), `keel-version`, and `token` (`github.token`; a PAT or App token
makes the bundle push trigger the cover check). Its steps:
1. Check out the PR's head branch with full history and the token.
2. Install keel as a static musl binary (`--target
   x86_64-unknown-linux-musl`), so one binary runs in any toolchain image.
   Checked by building keel for musl and running it in Alpine and in Debian
   bullseye.
3. Try to install `runsc` and register it with Docker. On any failure, use
   runc and say so.
4. `keel chain verify` on the checkout, stopping the job on failure, then copy
   `.keel/chain.jsonl` to `$RUNNER_TEMP/keel/chain.jsonl` (AC-6).
5. Start the container with `docker create`: read-only, tmpfs `/tmp`, `--cap-drop
   ALL`, `no-new-privileges`, `--user $(id -u):$(id -g)`, `--network`
   input, `--runtime runsc` when available. Mounts: the checkout at
   `/workspace`, `$RUNNER_TEMP/keel/sink`, `$RUNNER_TEMP/keel/posture` read-only,
   and the keel binary read-only. `KEEL_CHAIN_SINK` and
   `KEEL_RUNTIME_ATTESTATION` point into those mounts (AC-5).
6. Run `docker inspect`, then `keel runtime attest`, then `docker exec keel run
   <spec> --no-driver`. The run's verdict is recorded, not treated as fatal.
7. `keel runtime fold`, `keel export --chain`, `keel bundle verify`, stopping
   the job unless it passes. Then copy the bundle into `.keel/bundles/`, `git
   add -f`, commit as `github-actions[bot]`, and push (AC-7).

The tests parse the action and assert each of those properties. The Rust
commands are tested against fixture `docker inspect` JSON, a sink file and a
real chain, with no Docker needed.
